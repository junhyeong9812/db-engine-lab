## 3. 문제 정의 (TDD step 1)

14-01의 `ProtocolHandler`는 인증 실패 시 거부하는 분기를 이미 갖고 있는데, **판단해줄 상대가 없다.** 필요한 것은 두 가지 질문에 답하는 물건이다:

1. **인증(authentication)** — 너는 누구인가? 사용자 이름과 비밀번호가 맞는가.
2. **인가(authorization)** — 그래서 무엇을 할 수 있는가? 읽기만인가, 쓰기도 되는가, 관리자인가.

둘을 헷갈리면 안 된다. "로그인했다"는 "무엇이든 해도 된다"가 아니다. 실제 사고의 상당수가 인증은 있는데 인가가 없어서 생긴다 — 로그인한 일반 사용자가 관리자 기능을 부를 수 있는 식이다.

## 5. 구현 코드 (TDD step 3 — make it pass)

```kotlin
// src/main/kotlin/com/dbenginelab/auth/Auth.kt @ 5505edc
package com.dbenginelab.auth

import java.security.MessageDigest

// Q: enum이 sealed보다 적절?
enum class Privilege { SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, GRANT }
// <details><summary>A</summary>
// privilege는 닫힌 집합지만 enum이 simpler — 추가 시 enum value 추가만.
// </details>

data class Role(val name: String, val privileges: Set<Privilege>)

data class User(val name: String, val passwordHash: String, val roles: Set<String>)

object PasswordHasher {
    // Q: 왜 SHA-256? bcrypt 안 됨?
    fun hash(plain: String): String {
    // <details><summary>A</summary>
    // SHA-256 학습용. production은 bcrypt/argon2 (salt + work factor — brute-force 방어). SHA-256은 너무 빠름.
    // </details>
        val md = MessageDigest.getInstance("SHA-256")
        return md.digest(plain.toByteArray(Charsets.UTF_8)).joinToString("") { "%02x".format(it) }
    }
}

class AuthManager {
    private val users: MutableMap<String, User> = mutableMapOf()
    private val roles: MutableMap<String, Role> = mutableMapOf()

    fun addRole(role: Role) { roles[role.name] = role }
    fun addUser(name: String, plainPassword: String, roleNames: Set<String>) {
        users[name] = User(name, PasswordHasher.hash(plainPassword), roleNames)
    }
    fun authenticate(name: String, plainPassword: String): Boolean {
        val u = users[name] ?: return false
        // Q: == 비교 — timing attack 안전?
        return u.passwordHash == PasswordHasher.hash(plainPassword)
        // <details><summary>A</summary>
        // 학습용 — 진짜 production은 MessageDigest.isEqual() 같은 constant-time 비교 필요.
        // </details>
    }
    fun hasPrivilege(userName: String, p: Privilege): Boolean {
        val u = users[userName] ?: return false
        // Q: any { } 사용 — role hierarchy 없음?
        return u.roles.any { roles[it]?.privileges?.contains(p) ?: false }
        // <details><summary>A</summary>
        // flat RBAC — 사용자가 role 여러 개 가질 수 있고 union. hierarchy (admin > writer > reader)는 별도 graph 필요.
        // </details>
    }
}
```

## 7. 직접 깨뜨릴 과제 (먼저 해보고 답 펼치기)

**1.** SHA-256이 비밀번호 저장에 부적합한 이유는? 솔트가 없으면 같은 비밀번호를 쓴 두 사용자의 해시는?

<details><summary>답</summary>

**부적합한 이유: 너무 빠르다.**

SHA-256은 대량의 데이터를 빠르게 요약하라고 만든 함수다. 일반 GPU로 **초당 수십억 회** 계산할 수 있다. 비밀번호 해시가 유출되면 공격자는 후보를 초당 수십억 개씩 대입한다 — 8자리 영숫자 조합쯤은 몇 시간이면 전수 탐색이 끝난다.

비밀번호 전용 함수(**bcrypt·scrypt·Argon2**)는 반대로 **일부러 느리게** 설계됐다. work factor를 조절해 "한 번 계산에 0.1초"로 맞추면, 정상 로그인에는 무시할 수 있지만 공격자에게는 수십억 배의 비용이 된다. Argon2는 메모리까지 많이 쓰게 해서 GPU 병렬화를 어렵게 만든다.

**솔트가 없으면** — 같은 비밀번호는 **같은 해시**가 된다:

```kotlin
// (발췌 — 설명용. 파일이 아니므로 그대로 치지 말 것)
addUser("alice", "password123", …)
addUser("bob",   "password123", …)
// 둘의 passwordHash가 완전히 동일하다. 직접 찍어봐라.
```

결과:
1. **해시만 봐도 "이 둘은 같은 비밀번호"** 를 알 수 있다.
2. **레인보우 테이블**이 통한다 — 흔한 비밀번호의 해시를 미리 계산해둔 표와 대조하면 즉시 뚫린다.

솔트는 사용자마다 다른 무작위 값을 비밀번호에 붙여 해싱하는 것이고, 그러면 같은 비밀번호라도 해시가 달라져 위 둘이 모두 막힌다.
</details>

**2.** 비밀번호 비교가 문자열 `==`이다. 타이밍 공격이 무엇이고 왜 상수 시간 비교가 필요한가?

<details><summary>답</summary>

문자열 `==`는 **다른 문자를 만나는 즉시 멈춘다.** 그래서 앞부분이 많이 맞을수록 비교에 **더 오래 걸린다.**

```
저장된 해시: "a3f9c2..."
입력 "b..."    → 첫 글자에서 불일치 → 매우 빠름
입력 "a3f8..." → 네 번째에서 불일치 → 조금 더 느림
```

공격자가 이 시간 차이를 측정하면 **한 글자씩 정답을 좁혀갈 수 있다.** 전수 탐색이 `문자종류^길이`에서 `문자종류×길이`로 줄어든다 — 지수에서 선형으로 떨어지는 것이다.

`MessageDigest.isEqual`은 **길이가 같으면 항상 끝까지 비교**한다. 불일치를 발견해도 멈추지 않고 결과만 누적하므로 시간이 입력에 의존하지 않는다.

현실적으로 우리 코드에서 이 공격이 성공할까? **해시를 비교하므로 실익이 적다** — 해시 앞부분을 맞춰봐야 원본 비밀번호를 모르기 때문이다. 위험한 건 **API 토큰이나 HMAC 서명을 그대로 비교할 때**다. 그 경우 알아낸 값이 곧 인증 수단이 된다.

원칙은 하나다 — **비밀 값을 비교할 때는 항상 상수 시간 비교를 쓴다.** 실익을 따지지 말고 습관으로.
</details>

**3.** 인증은 성공했지만 권한이 없는 사용자가 쓰기를 시도하면? 그 검사가 어디서 일어나나?

<details><summary>답</summary>

**아무 데서도 일어나지 않는다.**

`AuthManager.hasPrivilege`는 만들어져 있고 `AuthTest`가 검증까지 하는데, **아무도 호출하지 않는다.** 14-01 `ProtocolHandler`를 보면:

```kotlin
// (발췌 — 설명용. 파일이 아니므로 그대로 치지 말 것)
private fun handleQuery(msg: Message.Query): ConnectionEvent {
    val sid = sessionId ?: return …("not authenticated")
    return try {
        val result = engine.execute(msg.sql)      // ← 권한 확인 없이 바로 실행
```

인증(로그인했는가)만 확인하고 **인가(무엇을 할 수 있는가)는 확인하지 않는다.** `reader` 역할만 가진 사용자도 `DROP TABLE`을 실행할 수 있다.

이게 §3에서 말한 "실제 사고의 상당수"의 모습이다 — 인가 로직이 **존재하는데 연결되지 않은** 상태. 코드 리뷰에서 `hasPrivilege`가 정의된 것을 보고 "권한 체크가 있구나"라고 판단하기 쉽다.

붙이려면 SQL이 어떤 동작인지 알아야 하므로, **파싱 후·실행 전**이 자연스러운 자리다:

```
Parser → Statement 종류 판별 → Privilege 매핑(SELECT→SELECT, DROP TABLE→DROP)
      → hasPrivilege 확인 → 통과하면 execute
```

14-00의 `DbEngine.execute`가 이미 `when (stmt)`로 종류를 가르고 있으니 그 자리가 유력하다.
</details>

**4.** 사용자를 추가·삭제하는 경로가 있나? 없다면 운영 중에 어떻게 계정을 관리하나?

<details><summary>답</summary>

`addUser`·`addRole`은 **메모리 맵에만** 쓴다:

```kotlin
// (발췌 — 설명용. 파일이 아니므로 그대로 치지 말 것)
private val users: MutableMap<String, User> = mutableMapOf()
```

즉 **재시작하면 전부 사라진다.** 영속화가 없다. 그리고 SQL이나 CLI로 계정을 만드는 경로도 없어서, **코드로 `addUser`를 부르는 방법밖에 없다** — 사실상 서버를 고쳐 재배포해야 계정이 바뀐다.

**재시작 없이 가능해야 하는 이유:**

1. **유출 대응.** 계정이 탈취됐을 때 즉시 잠가야 한다. "다음 배포 때 반영"은 대응이 아니다.
2. **퇴사자 처리.** 접근 권한 회수는 즉시성이 요구된다(감사 요건이기도 하다).
3. **재시작 자체가 장애다.** 계정 하나 추가하려고 전체 서비스를 끊을 수는 없다.

필요한 것: 사용자·역할을 **`Catalog`처럼 파일에 영속화**하고, `AdminCli`(단계 20)나 SQL(`CREATE USER`)로 조작하는 경로를 여는 것. 그리고 그 조작 자체에 권한이 필요하다(`Privilege.GRANT`가 이미 enum에 있는데 역시 안 쓰인다).

**만들어두고 안 쓰는 것들**이 이 세션에 세 개나 있다 — `hasPrivilege`, `Privilege.GRANT`, 그리고 영속화. 15-01이 "최소 구현"이라고 못 박은 범위가 어디까지인지 정확히 보여준다.
</details>
