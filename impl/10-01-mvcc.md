## 0. 참조

## 1. 만족시킬 invariant (Snapshot Isolation)

- **CI-1**: 트랜잭션은 **자기 snapshot 시점에 커밋된** 데이터만 본다.
- **CI-2 (Repeatable read)**: 같은 읽기를 두 번 하면 같은 결과가 나온다. 그 사이 다른 트랜잭션이 커밋해도 마찬가지다.
- **CI-3**: 미커밋 트랜잭션의 변경은 다른 snapshot에 보이지 않는다.

## 3. 문제 정의 (TDD step 1)

09-02의 락 모델은 정확하지만 **읽기와 쓰기가 서로를 막는다.** 한 시간짜리 보고서 조회가 그동안 모든 쓰기를 세워버린다. 실제 DB가 이 문제를 푼 방식이 MVCC다.

발상을 한 문장으로: **값을 덮어쓰지 말고 새 버전을 쌓아라.** 그러면 쓰는 사람은 새 버전을 만들고, 읽는 사람은 과거 버전을 계속 읽는다. 아무도 아무도 기다리지 않는다.

그러려면 각 버전이 **언제 태어나고 언제 죽었는지**를 알아야 한다:
- `xidStart` — 이 버전을 만든 트랜잭션 번호
- `xidEnd` — 이 버전을 지운(또는 덮은) 트랜잭션 번호

그리고 읽는 쪽은 **snapshot**(내가 시작한 시점의 번호)을 들고, 그 시점 기준으로 "이 버전이 나에게 보이는가"를 판정한다. 이 판정 규칙 하나가 MVCC의 전부다.

삭제도 값을 지우지 않는다. **tombstone**(값이 null인 버전)을 하나 더 쌓는다. 과거 snapshot은 여전히 옛 값을 본다.

주의 — SI가 모든 이상현상을 막지는 못한다. **어떤 것을 막고 어떤 것을 못 막는지**는 10-02에서 테스트로 못 박는다.

## 5. 구현 코드 (TDD step 3 — make it pass)

```kotlin
// src/main/kotlin/com/dbenginelab/mvcc/MVCCStore.kt @ 5505edc
package com.dbenginelab.mvcc

import java.util.Collections
import java.util.concurrent.ConcurrentHashMap
import java.util.concurrent.atomic.AtomicLong

class MVCCStore<K, V> {

    data class Version<V>(
        val value: V?,
        val xidStart: Long,
        @Volatile var xidEnd: Long = INFINITY,
    ) {
        companion object { const val INFINITY: Long = Long.MAX_VALUE }
    }

    data class Snapshot(val xid: Long, val active: Set<Long>) {
        // Q: isVisible 5조건 각각이 무엇 보호?
        fun isVisible(v: Version<*>): Boolean {
        // <details><summary>A</summary>
        // Update semantics — 같은 key의 새 insert는 옛 버전을 terminate. 한 시점 한 visible version (SI invariant).
        // </details>
            if (v.xidStart > xid) return false
            if (v.xidStart in active) return false
            if (v.xidEnd == Version.INFINITY) return true
            if (v.xidEnd > xid) return true
            if (v.xidEnd in active) return true
            return false
        }
    }

    private val chains: ConcurrentHashMap<K, MutableList<Version<V>>> = ConcurrentHashMap()

    @Synchronized
    fun insert(key: K, value: V, xid: Long) {
        val chain = chains.getOrPut(key) { mutableListOf() }
        chain.firstOrNull { it.xidEnd == Version.INFINITY }?.xidEnd = xid
        chain.add(Version(value, xid))
    }

    @Synchronized
    fun delete(key: K, xid: Long) {
        val chain = chains[key] ?: return
        chain.firstOrNull { it.xidEnd == Version.INFINITY }?.xidEnd = xid
        chain.add(Version(null, xid))
    }

    @Synchronized
    fun get(key: K, snapshot: Snapshot): V? {
        val chain = chains[key] ?: return null
        for (i in chain.indices.reversed()) {
            val v = chain[i]
            if (snapshot.isVisible(v)) return v.value
        }
        return null
    }

    @Synchronized
    fun versionCount(key: K): Int = chains[key]?.size ?: 0
}

class SnapshotProvider {
    private val nextXid = AtomicLong(1)
    private val active: MutableSet<Long> = Collections.synchronizedSet(mutableSetOf())

    @Synchronized
    fun begin(): MVCCStore.Snapshot {
        val xid = nextXid.getAndIncrement()
        active.add(xid)
        return MVCCStore.Snapshot(xid, active.toSet() - xid)
    }

    @Synchronized
    fun commit(snapshot: MVCCStore.Snapshot) { active.remove(snapshot.xid) }
}
```

## 7. 직접 깨뜨릴 과제 (먼저 해보고 답 펼치기)

**1.** 가시성 판정에서 `xidEnd` 검사를 지워라. 어느 테스트가 깨지나? 삭제된 데이터가 어떻게 보이나?

<details><summary>답</summary>

먼저 참고 실측 — **가시성 판정을 통째로 무시**(`isVisible` 호출 자체를 없애고 항상 최신 버전 반환)하면 **mvcc 테스트 10개 중 6개가 실패한다.** MVCC의 거의 전부가 이 한 줄에 달려 있다는 뜻이다.

`xidEnd` 검사만 지우면 범위가 좁아진다. `isVisible`의 뒷부분 세 줄이 그것이다:

```kotlin
// (발췌 — 설명용. 파일이 아니므로 그대로 치지 말 것)
if (v.xidEnd == Version.INFINITY) return true   // 아직 안 지워짐 → 보인다
if (v.xidEnd > xid) return true                 // 내 snapshot 이후에 지워짐 → 나에겐 보인다
if (v.xidEnd in active) return true             // 지운 tx가 아직 미커밋 → 나에겐 보인다
return false                                     // 내 snapshot 이전에 지워짐 → 안 보인다
```

지우고 무조건 `true`로 두면 **`return false`가 사라진다** → 삭제가 아무에게도 반영되지 않는다. `delete 후 새 snapshot 안 보고 옛 snapshot 봄`이 실패한다.

`xidStart`는 **"언제 생겼나"**, `xidEnd`는 **"언제 사라졌나"** 다. 둘이 함께 있어야 "내 snapshot 시점에 이 버전이 살아 있었는가"라는 구간 판정이 성립한다. 하나만으로는 시간의 한쪽 끝만 아는 셈이다.
</details>

**2.** 삭제를 tombstone 대신 실제 제거로 바꿔라. 과거 snapshot을 들고 있는 트랜잭션에게 무슨 일이 일어나나?

<details><summary>답</summary>

**과거를 볼 수 없게 된다.** MVCC의 전제가 무너진다.

```kotlin
// (발췌 — 설명용. 파일이 아니므로 그대로 치지 말 것)
// 현재 (tombstone)
fun delete(key: K, xid: Long) {
    chain.firstOrNull { it.xidEnd == INFINITY }?.xidEnd = xid   // 옛 버전에 "여기서 끝" 표시
    chain.add(Version(null, xid))                                // null 버전 추가
}
// 실제 제거로 바꾸면
fun delete(key: K, xid: Long) { chains.remove(key) }
```

`chains.remove(key)`를 하면 **체인 전체가 사라진다.** 그 키를 읽던 옛 snapshot도 이제 `null`을 받는다 — 자기 시점에는 분명히 존재했던 데이터인데.

`delete 후 옛 snapshot은 보고 새 snapshot은 못 봄` 테스트가 정확히 이걸 잡는다.

핵심 원리: **MVCC에서 삭제는 "지우는 것"이 아니라 "끝 시각을 적는 것"이다.** 데이터는 그대로 두고 유효 구간만 닫는다. 그래야 그 구간 안에 있는 snapshot이 계속 볼 수 있다.

그래서 MVCC DB에서 `DELETE`는 **디스크 공간을 즉시 돌려주지 않는다.** 오히려 버전이 하나 늘어난다. 이 성질이 다음 과제로 이어진다.
</details>

**3.** 버전이 무한히 쌓인다. 100만 번 갱신한 키의 읽기 비용은? 실제 DB는 이 문제를 어떻게 푸는가?

<details><summary>답</summary>

```kotlin

    for (i in chain.indices.reversed()) {       // ← 뒤에서부터 선형 탐색
        if (snapshot.isVisible(chain[i])) return chain[i].value
```

**최신 버전을 원하면 O(1)이지만, 오래된 snapshot일수록 앞쪽까지 걸어야 하므로 최악 O(버전 수)** 다. 100만 번 갱신했으면 최대 100만 번 비교. 게다가 그 100만 개가 전부 메모리에 남아 있다.

실제 DB의 해법:

- **PostgreSQL — VACUUM**: 어떤 활성 snapshot에도 보이지 않는 죽은 버전(dead tuple)을 찾아 공간을 회수한다. 자동으로 도는 autovacuum이 있고, **이게 밀리면 테이블이 부풀어 오른다**(table bloat). 운영에서 가장 흔한 PostgreSQL 이슈 중 하나다.
- **MySQL InnoDB — undo log + purge**: 옛 버전을 테이블이 아니라 별도 undo 영역에 두고, 필요 없어지면 purge 스레드가 지운다.

공통점은 **"어떤 버전이 더는 필요 없는지"를 판정하려면 가장 오래된 활성 snapshot을 알아야 한다**는 것이다. 그래서 **오래 열려 있는 트랜잭션 하나가 전체 정리를 막는다** — "idle in transaction" 세션이 위험한 이유다.

우리 코드에는 정리 기능이 아예 없다. 10-01 §0이 "in-memory 데모"라고 못 박은 이유다.
</details>

**4.** 두 트랜잭션이 같은 키를 각자의 snapshot에서 읽고 각자 갱신한 뒤 둘 다 커밋하면?

<details><summary>답</summary>

**둘 다 성공하고, 나중에 커밋한 쪽만 남는다.** 먼저 커밋한 쪽의 갱신은 사라진다.

```
초기: key=1 → "init"
tx1 시작, tx2 시작 (둘 다 "init"을 봄)
tx1: insert(1, "tx1-update")   → 성공
tx2: insert(1, "tx2-update")   → 성공 (아무도 안 막는다)
둘 다 commit
결과: "tx2-update"  ← tx1의 갱신은 흔적도 없다
```

10-02의 `lost update 미방지` 테스트가 이 동작을 **고정**하고 있다. "버그가 재현되는 것을 확인하고 통과하는" 테스트다.

현실로 옮기면 이렇다 — 잔고 1000원에서 두 창구가 각각 100원을 출금한다. 둘 다 1000을 읽고 각자 900을 쓴다. **200원이 나갔는데 잔고는 900이다.**

막으려면 커밋 시점에 **"내 snapshot 이후 이 키가 바뀌었나"**를 확인하고, 바뀌었으면 나중 쪽을 abort시켜야 한다. 이를 **first-committer-wins**라 하고, 진짜 Snapshot Isolation의 필수 요소다. 우리 구현에는 없으므로, 엄밀히 말하면 **우리가 제공하는 것은 SI보다 약하다.** 10-02에서 그 라벨을 정확히 붙인다.
</details>
