## Straggler이란?
### 1. 낙오자, 뒤쳐진 사람이라는 뜻으로, 분산 시스템에서는 여러 대에 일을 나눠줬을 때 유독 느리게 끝나는 한대를 가리킨다.
   문제는
```text
작업을 10대에 분산, 응답을 전부 기다려야 함

  Node 1 ██ 10ms
  Node 2 ██ 12ms
  Node 3 ██ 9ms
  ...
  Node 9 ██ 11ms
  Node 10 ████████████████████ 800ms   ← straggler

  전체 완료 시간 = 800ms
```
9대가 아무리 빨라도, 전체 응답 시간 = 가장 느린 한대의 시간이 된다. 이걸 tail latency문제라 부른다.

### 2. 왜 하필 그 한 대가 느려지는가?
특별한 고장이 아니라 평범한 시스템에서 상시로 일어나는 일이다.
원인 --> 설명
SSD GC      --> 하필 그 순간 그 디스크가 가비지 컬렉션 중
JVM GC      --> Full GC로 수백 ms 정지
CPU 경합      --> 같은 머신의 다른 프로세스, 컨테이너 이웃(noisy neighbor)
네트워크        --> 스위치 큐잉, 재전송, 일시적 혼잡
백그라운드 작업    --> 로그 로테이션, 백업, 인덱스 재구축, 모니터링 에어전트
하드웨어 열화     --> 발열로 인한 스로틀링, 디스크 재할당 섹터 증가
데이터 편중      --> 그 노드에만 유독 큰 파티션이 배정된다(data skew)

### 왜 규모가 커질수록 심각해지는가?
여기가 핵심이다. 개별 노드가 아주 가끔만 느려도, 노드 수가 많으면 거의 매번 걸린다.
노드 하나의 느릴 확률이 1%(p99에 해당)라고 하면:
```text
전부 빠를 확률 = 0.99^N

N=1    → 99%    느릴 확률 1%
N=10   → 90%    느릴 확률 10%
N=100  → 37%    느릴 확률 63%
N=1000 → 0.004% 느릴 확률 사실상 100%
```
100대에 요청을 뿌리면 3분의 2의 확률로 매번 straggler를 만난다. 각 노드는 99% 건강한 상황에서도 발생
Google의 Jeff Dean이 쓴 "The Tail at Scale"이라는 논문이 이 문제를 정리한 것으로 유명하다. 
요지는 "규모가 커지면 평균은 의미가 없고 꼬리(p99, p999)가 사용자 경험을 지배한다".

### 4. 대응 방법
#### 1. Quorum - 전부 기다리지 않기
BookKeeper의 Qa가 정확히 이 기법이다.
```text
Qw=3에 쓰고, Qa=2만 기다림

  B1 ██ 5ms   ✓
  B2 ██ 6ms   ✓  ← 2개 도착, 여기서 즉시 성공 처리
  B3 ████████████ 200ms  (계속 쓰긴 하지만 안 기다림)

  응답 시간 = 6ms
```
3대 중 1대가 느려도 영향을 받지 않는다. "다수만 응답하면 된다"는 규칙 하나로 straggler를 구조적으로 무력화한다.
반면 Kafka의 "acks=all"은 ISR 전원을 기다리므로, 팔로워 한 대가 GC에 걸리면 프로듀서의 응답 시간이 그대로 튄다.

#### 2. Hedged/Speculative Request -- 미리 한번 더 보내기
```text
요청 전송 → p95 시간(예: 50ms) 지나도 응답 없음
         → 다른 노드에 같은 요청을 하나 더 보냄
         → 둘 중 먼저 오는 것 채택, 나머지는 취소
```
여분의 부하는 5%정도만 늘면서 tail latency를 크기 줄일 수 있다. Cassandra,gRPC등에서 사용

#### 3. Speculative Execution - 배치 작업에서
MapReduce/Spark가 쓰는 방식이다. 태스크가 유독 느리면 같은 테스크를 다른 노드에서 중복 실행하고 먼저 끝난 쪽을 채택한다.

#### 4. Backup /Tied Request 
두 노드에 동시에 보내되 "다른 쪽에서 지가헀으면 취소하라"는 정보를 함께 넘겨 중복 작업을 최소화한다.

#### 5. 애초에 안만들기
- 부하 분산을 정교하게(data skew 제거)
- 백그라운드 작업 스케줄을 노드마다 어긋나게
- 읽기/쓰기 디스크 분리 <- BookKeeper의 journal/ledger분리가 이것
- JVM GC 튜닝, 또는 힙 밖으로 데이터 빼기 <- Kafka가 페이지 캐시를 쓰는 이유 중 하나

### straggler는 앞서 다룬 주제들이표면에 들어나는 방식이다.
```text
SSD GC로 그 디스크만 잠깐 느려짐
JVM Full GC로 그 브로커만 잠깐 멈춤
뒤처진 컨슈머의 랜덤 읽기가 쓰기 디스크를 점유
        ↓
그 노드가 straggler가 됨
        ↓
전부 기다리는 설계라면 → 전체 p99 latency 폭증
```
### 세 시스템의 선택을 straggler관점에서 본다면
Kafka -> JVM 힙을 안 써서 GC straggler를 예방, 하지만 acks=all은 전원 대기라 발생하면 그대로 노출
BookKeeper -> Qa 정족수로 회피, 디스크 분리로 읽기-쓰기 간섭도 예방
Redpanda -> JVM 자체를 제거하고 thread-per-core로 스케줄링 지터를 예방한다.
즉 평균을 좋게 만드는 것과 꼬리를 짧게 만드는 것은 다른 문제이며, 분산 시스템 설계에서는 후자가 훨씬 어렵다.
