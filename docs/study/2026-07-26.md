# SeqScan.kt
heap.scan()은 Sequence {} 빌더로 만들어져서 호출한 순간엔 아무것도 읽지 않는다.
페이지를 fetch하지도, 튜플을 디코드하지도 않는다.
소비자가 첫 튜플을 꺼내려고 할 때 비로소 블록이 돌기 시작하고, yield 지점에서 멈춘다.
다만 이때 완전히 1개씩도 아니고, 실제로는 페이지 1장 단위이다.
TableHeap.scan()을 보면:
```java
for (pageNo in 0 until pagedFile.pageCount()) {
    val page = bufferPool.fetchPage(...)
    val tuples: List<Tuple> try {
        ... repeat(count) {list += Tuple.decode(...)} // 이 페이지것만 List로 만듦
    } finally {
        bufferPool.unpinPage(page.id, isDirty = false) // 넘기기 전에 unpin    
    }
    yieldAll(tuples) // 여기서 하나씩 흘려보도록 설계된다.
}
```

페이지 0을 fetch -> 그 페이지 안의 튜플만 전부 디코드 해서 List로 만들고 -> unpin -> 그 리스트를 하나씩 내보낸다.
페이지 0이 다 소진돼야 페이지 1을 fetch한다. 100장짜리 테이블이면 메모리에 올라와 있는건 항상 한 장 분량이지 100장 분량이 아니다.
이때 페이지 단위로 list를 만드는 이유는 unpinPage가 yieldAll 앞에 있기 때문이다.
yield 지점에서 코루틴이 멈춰있는 동안 그 페이지가 계속 pin된 채로 잡혀있으면 소비할때 튜플 하나받고 딴짓하는 사이 버퍼풀 슬롯이 묶여버린다. 그래서
디코드(=힙 메모리로 복사)를 끝내고 pin을 해놓은 뒤 넘기는 것.

재정리
pin이 막는건
```java
private fun evictOne() {
    val victim = pages.values.firstOrNull { it.pinCount == 0 }
        ?: throw StorageError.AllPagesPinned(capacity)
    ...
}
```
이때
pages는 LinkedHashMap(capacity, 0.75f, true) -> accessOrder=true라 LRU순서이다.
자리가 꽉 차면 오래된 것부터 흝으면서 pinCount가 0인 첫페이지를 골라 내보내는데 이때 pin된 페이지 후보에서제외된다.
전부 pin이 되면 오류가 나옴.

그래서 yield 앞에서 unpin하는 이유는 이렇게 됩니다: 
yield에 멈춰 있는 동안은 소비자가 언제 다시 꺼낼지 모릅니다 — 영원히 안 꺼낼 수도 있고(.first() 하나 받고 버리기), 
그 사이에 다른 테이블을 통째로 스캔할 수도 있죠. 그동안 pin을 쥐고 있으면 256칸짜리 풀에서 한 칸이 무기한 묶입니다. 
스캔이 중첩되면(조인 같은 것) 묶이는 칸이 누적되고, 결국 AllPagesPinned로 죽습니다.

지금처럼 디코드 끝내고 unpin한 뒤 넘기면, 소비자가 중간에 순회를 포기해도 pin은 이미 반납된 상태라 새는 곳이 없습니다.

정리하면 — "다른 사람이 못 쓰니까"가 아니라 **"버퍼풀 슬롯이 무기한 묶이니까"**이다.
