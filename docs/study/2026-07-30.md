## TableHeap
테이블 스키마를 받고, 페이지 파일과 버퍼풀의 객체 좌표를 받는다.
init을 통해 
페이지 파일이 없으면 lastPageNo가 -1이 되어 fetchPage가 PageNotFound로 터진다. 그래서 "항상 최소 한 장은 있다"를 생성자에서 보장해 두고, insert는 그전체를 믿고 쓰게 한다.

### insert메서드의 경우
튜플을 받으면,
튜플의 스키마와 받은 스키마 즉 서로 같은 테이블의 스키마인지 비교하고,
튜플 데이터를 encode하고 엔트리 사이즈는 앞에 4바이트는 데이터 길이 자리이고,그 뒤 파일길이만큼 할당해서 크기를 만들고,
만약 페이지의 전체 사이즈보다 튜플이 크다면, 예외를 발생시키고,
라스트페이지 번호를 통해 마지막 페이지를 버퍼풀에서 가져온다.
그리고 마지막에서 프리오프셋과 엔트리 사이즈를 더했을때 페이지 사이즈에 다 들어가는 지 검사하고 다 들어간다면,
튜플을 마지막페이지에 작성 그리고 튜플 카운트랑 오프셋을 수정하고 리턴하고 마지막에 핀을 풀어서 isDirty로 true로 하면 이 페이지는 메모리 내용과 다르다는 의미이며,
버퍼풀이 다 차서 버퍼풀에서 나갈때 명시적 호출이나 내부적 close일 경우에 저장된다.
만약 저 조건이 맞지않는다면, 새로운 페이지를 만들고,
그 안에 새롭게 데이터를 작성한다.


### scan메서드의 경우
스퀸스로 튜플을 순회하면서 페이지 번호가 0과 페이지카운트 사이 즉 데이터를 페이지를 순회하면서,
튜플 리스트에 디코딩해서 반복문으로 디코딩을 하고 리스트로 만들고, list결과가 tuples에 들어간다.
그리고 스캔을 요청하면 tuples의 내부객체를 순차적으로 내보내도록 만들 수 있다. 즉 next()로 tuples를 순회 시킬 수 있다.

#### 이부분에서 내가 해갈린 부분.
yieldAll(tuples)에 대한 논리
yieldAll은 tuples배열 전체를 기준으로 내부에 1개의 데이터를 코루틴으로 순차적으로 반환한다. 즉
for (t in tuples) yield(t)이며
즉 소비자가 next()를 호출할 때마다 리스트에서 하나 꺼내 주고 다시 멈춘다(suspend).
yieldAll은 "이 컬렉션 원소들을 전부 스퀸스에 이어 붙여라"는 뜻이지, "리스트 하나를 통째로 값으로 준다는 의미가 아니다."
(통째로 주려면 yield(tuples)이고, 그러면 타입이 Sequence<List<Tuple>>이 된다.)

그렇기 때문에 실제 논리를 보면,
```text
페이지 0 fetch → 페이지 0의 튜플 전부 디코드해서 list에 담음 → unpin
   → yieldAll: 하나씩 하나씩 하나씩 (여기서 멈췄다 재개 반복)
페이지 1 fetch → ... 반
```
이렇게 보면 list에서 페이지 코드를 디코드해서 미리 리스트 메모리에 올린다.
그래서 소비자(즉,next()호출 대상)가 튜플 하나만 가져가도 페이지 0의 튜플은 이미 전부 메모리에 디코드된 상태이다.
이떄 페이지1은 아직 손대지 않은 상태.
즉 시퀸스 전체를 메모리에 올리진 않지만, 최소 한 페이지 분량은 미리 만들어 둔다.


### 현 insert문제
현 insert에는 오직 마지막 페이지만 보기 때문에 앞쪽 페이지에 공간이 남아 있어도 절대 재사용하지 않는다.
마지막 페이지가 꽉 차면 무조건 새 페이지를 붙인다. 그래서 진짜 DB가 되려면 "어느 페이지에 얼마나 빈 공간이 있나"를 관리하는 free space map을 둔다.
지금은 삭제 기능이 없어서 문제가 안되지만, 삭제가 들어오는 순간 중간 페이지에 구멍이 나도 재사용 못하니 이부분은 추후바꿔야된다.
