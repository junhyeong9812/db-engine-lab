# volatile

private volatile boolean running = true;

해결하려는 문제: JVM과 CPU는 성능을 위해 변수 값을 레지스터나 CPU 캐시에 올려두고 재사용한다.
그래서 이런 코드가 문제가 된다.
```java
  // 스레드 A                                                                                                                                                                                                                       
  while (running) { doWork(); }                                                                                                                                                                                                     
                                                                                                                                                                                                                                    
  // 스레드 B                                                                                                                                                                                                                       
  running = false;  // A를 멈추려고 함
```
volatile이 없으면 스레드 A는 running은 캐시된 값으로만 읽어서, B가 false로 바꿔도 영원히 루프를 돌 수 있다.
JIT컴파일러가 아예 while(true)로 최적화해버리기도 한다.

volatile이 보장하는 것 두 가지:
1. 가시성 - 쓰기는 즉시 메인 메모리에 반영되고, 읽기는 항상 메인 메모리에서 가져온다. B가 바뀌면 A가 다음 읽기에서 바로 본다.
2. happens-before 순서 - volatile 쓰기 이전에 실행된 모든 쓰기는, 그 volatile을 읽은 스레드에게 함께 보인다.
    즉 volatile변수가 일종의 동기화 지점 역할을 해서, 그 앞의 일반 필드 쓰기들까지 같이 전파된다.

보장하지 않는 것: 원자성, count++는 읽기->증가->쓰기 3단계라서 volatile이어도 두 쓰레드가 동시에 하면 증가가 유실된다.

정리하면 synchronized가 "상호 배제 + 가시성"을 주는 데 비해, volatile은 락 없이 가시성만 싸게 얻는 도구이다.
플래스 변수나 "한 스레드만 쓰고 여럿이 읽는" 값에 적합하다.
