## LSM-Tree란?
### 해결하려는 문제
DB의 고민은 이거다. 인덱스는 정렬되어 있어야 검색이 빠른데, 
정렬을 유지하려면 중간에 끼워넣어야 하고, 중간에 끼워넣으면 랜덤 쓰기가 된다.
```text
B-Tree에 새 데이터 삽입:
  "id=500을 넣어야 하네"
  → 트리를 타고 내려가 위치 찾기 (랜덤 읽기)
  → 그 페이지를 고쳐서 다시 쓰기 (랜덤 쓰기)
  → 페이지가 꽉 찼으면 분할 → 부모도 수정 → 연쇄 랜덤 쓰기
```
LSM-Tree의 답은 "정렬을 나중으로 미루자"이다.

### 기본 구조
```text
메모리
┌────────────────────────────┐
│  MemTable  (정렬된 자료구조)  │  ← 여기에 먼저 씀
└────────────────────────────┘
         │ 꽉 차면 통째로 flush (순차 쓰기!)
         ↓
디스크
┌────────────────────────────┐
│  SSTable  (정렬된 불변 파일) │  ← 한 번 쓰면 절대 수정 안 함
│  SSTable                   │
│  SSTable ...               │
└────────────────────────────┘
```
쓰기 경로
1. WAL에 append -- 장애 대비용 로그, 순차 쓰기
2. MemTable에 삽입 -- 메모리라서 정렬 유지가 저렴
3. MemTable이 꽉 차면 -- 이미 정렬된 상태 그대로 파일로 쏟아낸다. 완전한 순차쓰기
4. 그 파일(SSTable)은 불변, 이후 절대 고치지 않음

 핵심: 랜덤 쓰기를 메모리에 흡수하고, 디스크에는 순차 쓰기만 내려보낸다.
수정과 삭제도 쓰기이다.
```text
id=42를 "B"로 수정  →  기존 것 안 고치고 새로 (42, "B") 씀
id=42를 삭제        →  (42, tombstone) 이라는 삭제 표시를 씀
```
읽을 때 최신 것을 우선하면 되니까, 여기서 append-only + 불편이라는 점에서 Kafka-SSD의 FTL과 정확히 같은 발상이다.

### 읽기와 그 대가
쓰기가 편해진 대가는 읽기가 치른다. 같은 key가 여러 SSTable에 흩어져 있을 수 있다.
```text
"id=42 줘"
  → MemTable 확인
  → SSTable-1 확인 (최신)
  → SSTable-2 확인
  → SSTable-3 확인 ...    ← 최악의 경우 전부 뒤짐 (read amplification)
```
그래서 보조 장치를 단다.
장치 -------> 역할
Bloom Filter -------> "이 SSTable에 key 42가 확실히 없다"를 메모리에서 즉답. 없는 파일은 아예 안 읽는다.
Sparse Index  -------> SSTable 안의 위치를 대략 찾아주는 색인
SSTable 내부 정렬 -------> 정렬돼 있으니 이진 탐색 가능. 범위 스캔도 순차 읽기
